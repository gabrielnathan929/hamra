# Contributing

Hamra is a personal NixOS + Home Manager configuration library, open for
anyone to study, copy, or adapt. Pull requests are welcome, as long as they
respect the project's rules.

## Before making changes

Read [`AGENTS.md`](AGENTS.md) — it defines the structural rules (NixOS vs
Home layers, categories by app shape, toggle modules, host roles).
[`ARCHITECTURE.md`](ARCHITECTURE.md) explains where the configuration that
boots each machine comes from.

## Fork contract

Hosts **never flow upstream**. Each host is an atomic personal unit:

- `hosts/<machine>/` (`configuration.nix` import shim, `config/system.nix`,
  `config/hardware.nix`, `config/desktop.nix`, `config/programs-core.nix`,
  `config/programs-optionals.nix`, `config/home.nix`) and `hardware-configuration.nix` —
  machine identity, choices and toggles. Yours alone. Keep them in your fork
  and never submit them in a PR.
- Contributions are the library and its documentation: `modules/`,
  `flake/`, `docs/`, `.github/`, root `*.md`.

CI enforces this: a PR that touches anything under `hosts/` fails the
`personal-layer guard` check. A maintainer may still merge an intentional
change by adding the `personal-layer` label.

In your fork everything is yours — generate hosts with `hamra-init` and edit
them freely; pulling upstream updates stays conflict-free because your files
do not exist upstream.

## Versioning your hosts (in your fork)

"Never push hosts upstream" does not mean "never version them".
Your fork is your version control: hardware and host configs are
committed and pushed to **your own GitHub fork** (your `origin`), which backs
up your machines like any Nix config repo.

One-time setup:

```bash
gh repo fork gabrielnathan929/hamra --clone
cd hamra
git remote add upstream https://github.com/gabrielnathan929/hamra
```

Day to day — your machines, versioned in your fork:

```bash
git add hosts/<your-machine>
git commit -m "hosts: <your-machine>"
git push origin main
```
Pulling library updates (your hosts do not exist upstream, so this merge
is clean by construction):

```bash
git fetch upstream
git merge upstream/main
git push origin main
```

Contributing back — always branch from **upstream/main**, never from your
personal main, so your hosts stay out of the diff:

```bash
git switch -c feature/your-change upstream/main
# ...work...
git push origin feature/your-change
gh pr create --repo gabrielnathan929/hamra
```

Your host file is yours to edit freely — every toggle lives there. If a
change belongs in the project (a module fix, a new toggle, better defaults),
propose it upstream as a library change.

## Workflow (Git Flow)

1. Create the branch from `main`: `feature/<name>` (urgent production fix:
   `hotfix/<name>`).
2. Conventional commits: `feat`, `fix`, `refactor`, `chore`, `docs` — the
   release notes are generated by grouping on this prefix.
3. Open the PR against `main` and fill in the template (goal, cause, risks,
   tests).
4. CI must be green: formatting (alejandra), lint (`statix` + `deadnix`),
   evaluation (`nix flake check`) and build of all hosts.
5. Every merge to `main` triggers the automatic release: `release.yml`
   creates the next minor semver tag. Group related changes in the same PR
   to avoid burning a version on noise. Majors are manual (contract break:
   host removal, option renamed/removed).

## Golden rules (summary of AGENTS.md)

- One file per program; the option path mirrors the file path
  (`optionals/tui/yazi.nix` -> `hamra.programs.optionals.tui.yazi`).
- Package installation always in the NixOS layer; the Home layer is config
  only.
- No comments in code — names and `mkOption` `description` do the
  documenting.
- Hosts are named by machine (`samsung`, `acer`, `vm`); each host's hardware
  is generated on the machine itself and is **never** copied between hosts.
- Host role (NAS, VNC server) != personal preference: role toggles default
  `false` in the modules and are enabled on the host that performs the
  role.
- Secrets: never in plaintext and never in the Nix Store — `secrets/*.yaml`
  via sops-nix (instructions in AGENTS.md).

## Validate locally before the PR

```bash
nix develop
alejandra --check .
statix check .
deadnix .
nix flake check
```

For structural changes, prefer `nix run .#build-<host>` (build without
applying) before switch, and `nixos-rebuild test` before `switch`.
